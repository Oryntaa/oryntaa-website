The fastest way to sink a first release is to build all of it. Every feature you add before
launch is a bet placed before you have any evidence. A good MVP makes the smallest number
of bets that still answer the question the business is actually asking.

## Find the one thing the release has to prove

Every product has a central assumption — people will pay for this, this workflow is better,
this data is worth surfacing. The first release exists to test that assumption, not to be
feature-complete. We start by naming it out loud, because it decides everything after.

## Cut to the features that earn their place

With the assumption fixed, most of the backlog becomes optional. We keep the features that
directly prove the model and defer the ones that only matter once it is proven. This is not
about building less carefully; it is about building less, carefully.

## Foundations built to iterate

Shipping fast and shipping disposable are not the same thing. The MVP runs on the same
architecture, auth, and billing you would want at scale — so the second version is an
extension of the first, not a rewrite of it. Speed now should not mean a cliff later.

## Scope in phases, decide at each gate

We scope in stages with a decision point at each one: prove the value, harden what earns it,
then grow. You are never committing to the whole roadmap on day one — you are committing to
the next gate, with real evidence in hand before the next one.

An MVP done this way is not a smaller promise. It is a faster way to learn whether the
promise is worth keeping — before the budget that would have proven it is already spent.
